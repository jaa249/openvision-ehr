| D48 | Translations | **Our own small i18n code, no library** (`src/lib/i18n/`, a few hundred lines with comments). English is the source; other languages are drafted and shown as **drafts** ("Español (draft translation)") until a native eye-care professional reviews them, then `status: 'reviewed'`; volunteers translate through Hosted Weblate ([`TRANSLATING.md`](TRANSLATING.md)). **Files**: `messages/<namespace>/<locale>.json`, one flat JSON object per namespace and language (Weblate's "i18next JSON v4"); 17 namespaces exist from the start so later work never edits `catalog.ts`. The `server` namespace (form-action and API messages) is only built into the server, since SvelteKit keeps every `/server/` folder out of browser code. **Keys**: camelCase letters and digits, no dots; code uses `<namespace>.<key>` and the compiler rejects unknown keys. **Placeholders** `{name}`; **plurals** i18next-style `<key>_one` / `_other` (+ `_zero/_two/_few/_many` where a language needs them) chosen by `Intl.PluralRules`, falling back to `_other`, then English. **No HTML in messages**: a link, code or emphasis is a placeholder filled by `Msg.svelte`. A missing message shows English, then the key itself (never an error). **Language order**: a signed-in user's own choice (My settings), else the practice default (Settings → Practice, audited; chosen at first-run setup); the `ov_lang` cookie never overrides a signed-in user. Signed out: a valid `ov_lang` cookie, else (first-run setup only) the browser's language, else the practice default, else English. **Sign-in page language menu**: a GET form (`/login?lang=xx`, with a "Change" button that is hidden once JavaScript runs; with JavaScript a change applies at once) sets `ov_lang` (path /, SameSite=Lax, httpOnly, one year, not Secure because it holds no secret and plain-http LAN installs would drop it; anything that is not a known language code is ignored) and returns to `/login?chosen=1`. On sign-in, if the user never chose a language (pref `practice`) and changed the menu on that page (`langChosen=1`), the chosen language becomes their own pref (prefs are not audited); an explicit choice is kept. After every sign-in `ov_lang` is set to the user's language, so the sign-in page on that computer opens in it next time; signing out leaves it. Dates and numbers use the page language on the server and in the browser alike. **Not translated by us**: WHO ICD-11 titles (WHO's official language releases are loaded instead, D50); clinical text the user types and quick-pick and shorthand expansions stay exactly as entered (they are the legal record), and translating clinical vocabulary is a separate later decision. VA notation (20/20 vs 6/6) and paper size (Letter/A4) are practice settings to add later, not translations. **Right-to-left**: the html `dir` attribute is set from the language (Arabic is the first RTL language); page chrome uses CSS logical properties (`margin-inline-start`, `text-align: start`, ...) so it mirrors while English stays pixel-identical, and directional glyphs flip (`.flip-rtl`). **Clinical layouts are never mirrored**: the patient's right eye (OD) stays on the viewer's left, as when facing the patient, in every language, so OD | OS grids, drawings, gaze/cover/Amsler grids, charts and Rx tables carry `.eye-ltr` (labels inside still read right-to-left); values (sphere, IOP, 20/40, codes, MRN, dates, the shorthand bar) stay left-to-right and free text takes the direction of what is typed (rules in [`TRANSLATING.md`](TRANSLATING.md#right-to-left)) | Owner's direction 2026-10-07: usable internationally, while the owner works in English only. Paraglide 2 would add the inlang SDK, a compiler step and URL-based locales to an app with no runtime dependencies (offline desktop, auditability); we need a per-user language without changing URLs, files Weblate reads natively, plurals and placeholders |
| D49 | Code sets are downloaded, not shipped | OpenVision's package and git hold **no diagnosis code files**. An admin downloads the practice's code set in **Settings › Code sets** (or from the note under the code-set choice in Settings › Practice, where first-run setup lands): the server fetches the official zip (CMS ICD-10-CM FY2027, WHO ICD-11 MMS 2026-01 English; https only, 120 s, 50 MB), extracts the code file with our own small zip reader (no dependency; CRC-checked, limits against zip bombs), checks its **SHA-256 against the release pinned in `src/lib/codesets/releases.ts`** (else: "The downloaded file is not the expected release. Update OpenVision or import the file yourself."), stores the text gzip-compressed and otherwise unchanged in `OPENVISION_CODES_DIR`, else `<database folder>/codes`, and loads the table. **Offline**: the admin brings the official zip (or the text file in it) on a USB stick and imports it, same check. **Remove** deletes a set's codes unless the practice uses it. All three are admin only and audited (`settings.codes`: set, release, source, SHA-256). Until the set is downloaded the code finder and search APIs answer no codes with `notLoaded: true` and say "Diagnosis codes are not downloaded yet. An admin can download them in Settings › Code sets.", typed codes are refused with that message, and the findings engine suggests none. Saved diagnoses never depend on the table (they store code, title and, for ICD-11, URI). Development: `npm run codes:fetch` fills the git-ignored `codes/`, which a checkout reads last when `OPENVISION_CODES_DIR` is unset; tests needing the real files skip without them | Owner's direction 2026-10-07: each practice downloads only the code sets it needs, so the package carries no data it may never use. | D50 | ICD-11 titles in other languages | WHO publishes the ICD-11 MMS 2026-01 SimpleTabulation file in 14 languages besides English: **es, fr, zh, ar** (OpenVision's interface languages), **ru, pt, de, tr, uz, cs, kk, sv, sk, la** (available for later; WHO marks German a pre-release and Latin has titles only); probed 2026-10-07, there is **no Hindi** (nor Italian, Japanese or Korean) file, so Hindi users see English. Each file is pinned in `src/lib/codesets/releases.ts` (`ICD11_LANGUAGES`: URL, entry, SHA-256 of the entry text) and handled exactly like a code set (D49): Download from WHO or Import file (zip or the text in it), hash-checked, kept gzip-compressed and unchanged as `icd11_mms_2026-01_<lang>.txt.gz`, Remove; admin only and audited (`settings.codes` with `lang`), API `/api/admin/codesets/icd11/languages/<lang>[/download\|/import]`; listed under ICD-11 in **Settings › Code sets** with its status, licence line and official link. A script checked every file: the same 35,664 (Code, Linearization URI) pairs as English; WHO left some titles empty (none in tr, up to 6,618 in de), which then show in English. **Storage**: one migration adds `icd11_titles(lang, code, uri, title, search)` (titles joined to English by code; `search` is a folded copy for matching only), `icd11_titles_meta` (release, source file, SHA-256, rows, loaded_at per language) and `title_lang` on impression items and history issues.
